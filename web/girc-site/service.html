The hosted service · free, and the code is the same code

Post a stream, get the figures back.

The analysis is a Rust tool that reads a sequence and writes a report. To run it you would need a toolchain, a clone and a build. This is that same tool behind an HTTP endpoint, so you can find out what GIRC says about your content before you decide to embed anything.

It is not a different product and not a hosted-only feature: it is girc-bench with the report returned over the wire, running from the same source you can read and deploy yourself.

Is it awake?

This is a free instance on a shared host, which means two things you should know before you rely on it: it sleeps after fifteen minutes without a request, and the first request after that takes about a minute to answer. An uptime monitor pings it every five minutes to keep that from happening, and the state below is read from the service itself rather than from this page's build.

How to call it

One POST, one report

From a sequence

curl -sS -o report.json \
  -F "sequence=@foreman_cif.y4m" \
  "https://girc-portal.onrender.com/analyze?format=json"

The body is a Y4M sequence. The response is the same figures the benchmark writes.

For a script

curl -sS -o /dev/null -w '%{http_code}\n' \
  -F "sequence=@akiyo_cif.y4m" \
  "https://girc-portal.onrender.com/analyze?verify=1"

200 when the round trip is bit-exact and the report holds, 422 when it does not.

Limits

Request body8 MiB
Frames per request64
Wall-clock budget60 s
Concurrent requests1 — the free instance has a tenth of a core
Retentionnone: the sequence is held in memory for the request
What happens to your sequence

It is read into memory for the duration of one request, the report is written to the response, and the buffer goes. Nothing is stored: the analysis runs in a request-scoped temporary directory that is removed when the request ends, and the reports are not written to disk. If your content is confidential, run the benchmark yourself; the install page takes three commands.

Run it yourself

The service is not the product; the codec is

The hosted instance exists so you do not need a toolchain to see the output. Everything it does, a checkout does: the container definition and the service's own render.yaml are in the repository, so you can deploy the identical thing on your own host, or point the site at your own URL.

Container

git clone https://github.com/devansh0703/girc
cd girc
docker build -f deploy/Dockerfile -t girc-portal .
docker run -p 8000:8000 girc-portal
curl localhost:8000/health

Two honest caveats

The free instance has a tenth of a core and half a gigabyte of memory, so a long sequence will time out there and would not on your machine. And only one request is served at a time, so a queue behind a long sequence is the expected behaviour rather than a bug.

Neither of those is a property of the method. If either matters to you, that is the point at which running it locally is the right answer.
